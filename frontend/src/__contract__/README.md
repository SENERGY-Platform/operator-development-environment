# Contract fixtures

The JSON here was captured from a running ODE backend. `contract.ts` assigns each
file to the type `src/api.ts` declares for that endpoint, so `npm run build` fails
if the two ever disagree — a renamed or dropped field breaks the build instead of
becoming `undefined` at runtime in front of a developer.

**Three exceptions, worth knowing before you trust them.**

`selection.json` was emitted by the M2 API test harness rather than captured from a
platform, because M2 was built without platform access. It is still the backend's
own marshalling of its own types, which is what this check is about — but its
*values* are a fake's, and its device types are smaller than any real one.

`quick.json` is a real capture with one **hand-patched** field: each candidate's
`device` block was added by hand when it was introduced, again for want of a
platform. The ids and the names in that block are invented, so do not read them as
evidence of anything; the field set around them is still the backend's.

`profile.json`, `projection.json`, `sessions.json` and `override.json` are real
captures and carry `detector_version: "1.0.0"`, which the profiler has since left
behind — the counter, periodicity, FFT-resolution and hysteresis fixes took it to
1.1.0. That is not drift to repair: a capture records what the backend answered on
the day, and D25 puts the version in the cache key precisely so an old profile is
legible as old. It does mean these four cannot be regenerated without a platform,
and that a fresh capture will differ in more than the version string — the periods
in `profile.json` in particular were computed before the phantom weekly cycle was
removed.

The nine `chat_*`, `admin_*` and `session.json` files of M3, the two `kernel_*`
files of M4, the `chart_*` plus `charts.json` files of M5, the four `relation*` files
of M6, the eight `repo_*` files of M7 and the eight `experiment*` files of M8 and M9
were emitted by the API test harness for the same reason, and are regenerated by a test
rather than by curl:

```bash
ODE_WRITE_CONTRACT=$PWD/frontend/src/__contract__ go test ./pkg/api/ -run ContractFixtures
```

That is deliberately not a capture. Those endpoints need a configured LLM provider
and a chat session with history, a JupyterHub with a running pod, or a computed
profile for a chart to annotate — more setup than a capture script should own — and
emitting them from the handlers is the same guarantee, since it is still the backend
marshalling its own types. The M4 pair comes from the in-memory Hub in
`pkg/kernel/kerneltest`, so the kernel ids and the one listed file are a fake's. In
the M5 files the *points* are a fake's, one constant at a coarse bucket chosen so
the fixture stays a shape check rather than a large file, while the annotations are
a real profiler run over the harness fixture — so the confirmable field paths in
there are the backend's own.

The eight `repo_*` files of M7 are the least synthetic of the whole set: the status,
the tree, the file, the commit and the push come from a **real git working copy** in a
temporary directory, pushed to a **real bare repository**, so every field in them is
git's own answer rather than a fake's. Only `repo_connection.json` and
`repo_repositories.json` are invented, because GitHub's API cannot be had locally.
The clone URL in there is a `file://` path into a test's temporary directory, which
is what makes the rest real — do not read it as a URL that means anything.

The six `experiment*` files of M8 are split the way the M7 ones are, and the split
is worth knowing before reading a number out of them. `experiment.json`,
`experiments.json` and `experiment_launch.json` come from a **real git working
copy**: the commit SHAs in them are real commits of a real scaffolded repository in
a temporary directory, and `package_bytes` is the size of an actual
`git archive --format=zip` of that commit. The two runs in `experiments.json` are
from **two different commits** on purpose, because that is what §5.11 item 7 is
about and a fixture with one commit could not show it.

What *is* a double's: every metric, every Ray status, and the log line in
`experiment_logs.json`. Neither a Ray cluster nor an MLflow server can be had in a
unit test, so `rmse` falling from 0.42 to 0.31 in `experiment_results.json` is a
number a test wrote — do not read it as a result. The **shape** around it is the
backend's own, including the thing worth checking: `comparison_to_previous` carries
`lower_is_better` beside `direction`, because the direction is inferred from the
metric's *name* and a frontend that showed the verdict without the rule would be
presenting a naming convention as a judgement.

The two `experiment_interpretation*.json` files of M9 are the most composite of the
set, and it is worth being blunt about which half is which. The **mechanism** is
entirely real: the run was settled by the real poller reading the Ray double, the
summary was built by the real service, it was injected into a real chat session
through the real `chat.Engine` — past the real §3.3 cap check and the real
one-exchange-at-a-time rule — and the proposal was extracted from the reply by the
real parser and fingerprinted by the real hash. The decision in
`experiment_interpretation_decided.json` went through the real route and the real
validation.

The **words** are a fixture's. `interpretation` is a string a scripted stub
returned; no model ran, and reading it as an example of what an assistant says
about a run would be reading a test's prose as a finding. `proposal.text` is the
tail of that same scripted string, so the `proposal_id` beside it is a real hash of
a fake sentence — real enough to prove that a decision keyed on it survives a
recomputation, which is what it is there for, and meaningless as advice.

The evaluation criteria are the one part that is neither: they come from a **real
`evaluation.yaml` at a real commit**, parsed by the real reader, so `source`,
`goal_stated` and `threshold` are what a developer's own file said. The pair in
`experiment_results.json` is deliberate and is the thing to check a renderer
against: the primary criterion is a bare `"met": true`, and the secondary one is
the `{"status": "not_computed", "reason": "metric_not_reported"}` object, because
those two arms must render differently. A frontend that showed the object arm as a
failed criterion would be making exactly the claim D24 exists to prevent — the run
did not miss that target, nothing compared it.

`experiment_embed.json` is the least meaningful of the whole set and is here for
its field set alone. Both services in it are the test's own httptest servers, which
set no framing headers and answer 404 to `/` — so both come back `embeddable:
"yes"` with a status of 404, which is a combination no real deployment produces.
The verdicts that matter are covered in Go instead (`pkg/experiments/embed_test.go`
drives `X-Frame-Options: DENY`, a restrictive `frame-ancestors`, an allow-list and
an unreachable service). Read this file as "these are the keys", nothing more.

One field is absent rather than empty and that is not a mistake: the runs carry no
`session_id` tag, because the fixture launches through the HTTP route rather than
from a chat session. A launch that came from one would have it.

The M6 files are the second least synthetic. Only the two series behind them are
fabricated — an oven and a kitchen light, chosen so the real session detector finds a
split in each — and everything above that is computed: the thresholds are the
profiler's, and the contingency counts, the lift and the 06:00–12:00 exception window
in `relation.json` are the rule detector's own answer over them.

`relation_sets.json` also carries a device relationship graph, and its fixture is one
`models.Graph.Valid` accepts — a test asserts that, because a topology the platform
would reject proves nothing about what ODE does with a real one. The site meter in
there sits outside the Kitchen aspect on purpose: that is the cross-level pair a
sub-metering question is about, and a fixture where every device was already in the
aspect could not show it.

Recapture the M1 and M2 files from a platform with the commands below when you next
have one, and that part of this note goes away.

This is not decoration. Writing it caught four real defects on its first run:
`available_conversions` arriving as `null` rather than `[]` (which crashed the
candidate detail), an absurd ADF statistic on a deterministic series, harmonics of
the daily cycle reported as separate periods, and periodicity computed on a
counter's level instead of its rate.

It caught a fifth on the M3 pass, and a subtler one: two structs disagreed on the
name of the same field, and the one called `duration_ms` was carrying a
`time.Duration` — which marshals as *nanoseconds*. Both are plausible integers, so
nothing at runtime would have looked wrong. `tools.Millis` is the fix.

## Regenerating

Needed whenever the backend's JSON shape changes on purpose. Point `ODE` at a
platform, get a token, and re-capture:

```bash
TOKEN=...                       # a Keycloak access token with the developer role
BASE=http://localhost:8080
DIR=frontend/src/__contract__

curl -s -H "Authorization: Bearer $TOKEN" "$BASE/quick-profiles" > $DIR/quick.json

curl -s -X POST -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"intent":"forecast PV generation"}' "$BASE/selection" > $DIR/selection.json

# Any candidate's device and service from quick.json:
DEV=$(jq -r '.candidates[0].series_ref.device_id' $DIR/quick.json)
SVC=$(jq -r '.candidates[0].series_ref.service_id' $DIR/quick.json)

curl -s -X POST -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d "{\"device_id\":\"$DEV\",\"service_id\":\"$SVC\"}" "$BASE/profiles" > $DIR/profiles.json

PID=$(jq -r '.profiles[0].profile_id' $DIR/profiles.json)
curl -s -H "Authorization: Bearer $TOKEN" "$BASE/profiles/$PID" > $DIR/profile.json
curl -s -H "Authorization: Bearer $TOKEN" "$BASE/profiles/$PID/projection" > $DIR/projection.json
curl -s -H "Authorization: Bearer $TOKEN" "$BASE/profiles/$PID/sessions?limit=5" > $DIR/sessions.json
curl -s -H "Authorization: Bearer $TOKEN" "$BASE/timeseries/availability?device_id=$DEV" > $DIR/availability.json
curl -s -X POST -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"field_path":"value_semantics.unit","action":"correct","computed_value":"W","confirmed_value":"kW"}' \
  "$BASE/profiles/$PID/overrides" > $DIR/override.json
```

Then `npm run build`. Two things to keep in mind when a capture changes the shape:

- **`Loose<T>` in `contract.ts` widens string-literal unions to `string`.** A JSON
  import types every string as `string`, so without it the check fails on
  `confidence: "uncertain"` not being the union member it plainly is. Field sets
  and structure are still compared exactly, which is the point.
- **A field that is genuinely optional per variable must be optional in the
  type.** The provenance map is the live example: a variable with no
  characteristic carries no `value_semantics.characteristic_id` entry, so the map's
  value type admits `undefined`.

## What is deliberately not checked here

Values. This asks whether the frontend and the backend agree on the shape of the
payload, not whether a detector is right — that is what the Go fixture tests are
for (`pkg/profiler`, SPEC §5.4.14).
